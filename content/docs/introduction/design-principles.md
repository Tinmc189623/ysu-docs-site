## 内核不碰设备，也不产文档

两件事都不做，而且理由是同一条：**不该由内核管的东西，就别让它管。**

GPU 设备不在内核手里。`Device` 与 `Queue` 由调用方建好传进来，`render/mod.rs` 的模块注释写明这么切是为了两件事：内核能脱离窗口单独测试，设备的生命周期只归调用方。`examples/render_headless.rs` 就是这条的成果——它在没有显示服务的机器上自己建设备、渲到纹理、把像素读回来核对，验证着色器与图集真的产出了正确的像素。

文档内容也不在内核手里。`src/address.rs` 的模块注释把话写得很直白：内核不认识「自己提供的页面」这种说法，它只解析它拿到的文档，不生产文档。起始页、空白页、出错提示都是调用方的事，谁提供内容谁负责把 HTML 交进来。

## 中间产物都是公开类型

`src/lib.rs` 里十个模块全部 `pub`，没有一个是内部的。记号、节点树、样式表、计算样式、盒子树、显示列表——每一步的产物都是公开类型，各自能单独构造、单独验证。

这条不是顺手的风格，它决定了测试怎么写。想验选择器匹配，直接喂一段 CSS 和一棵节点树；想验布局，直接构造一棵盒子树；想验绘制，直接给一棵带几何的树。整条链只有做端到端验证时才需要跑全。

## 借协议，自己做领域

`Cargo.toml` 里的运行时依赖只有六个：`url`、`encoding_rs`、`cosmic-text`、`wgpu`、`rustls`、`webpki-roots`。

TLS 是密码学协议，URL 解析是标准化的字符串处理，字符集转换是查表，文本整形与栅格化是另一门手艺，GPU 是驱动接口——这五类都借现成的。剩下的 HTML 词法与树构建、CSS 词法与选择器、层叠与继承、布局、绘制、显示列表、HTTP 客户端，全部自己写。

分界大致是：**协议实现可以借，领域实现自己做。** HTML 树构建是渲染内核之所以为渲染内核的那部分，借不来。

## 判据是「换一套外壳还要不要重做」

地址解析、相对地址补全这类判断，看起来像界面问题，`src/address.rs` 把它们算作网页平台的行为。它可以借 `url` 这个库，但判断本身留在内核里。

判据写在那个文件的模块注释里：**换一套外壳之后，这个判断还要重新做一遍吗？** 要，那它就该在内核里。不然两套外壳各写一遍，「什么是文件路径」这种判断迟早会有出入。

## 拿外人能核对的标准当尺子

`tests/html5lib_tree.rs` 的注释里有一句关键的话：这批用例是各浏览器与 Servo 共用的那一份，不是为本项目定制的——拿它当尺子，「通过」这个词才有外人能核对的含义。

同一份注释还定了两条判据，都是为了让数字不虚高：只比对树，不比对错误条数（错误计数是另一件事，混在一起会让失败原因看不清）；片段解析的用例一起跑，不单独排除（挡在外面会让通过率虚高）。

## 解析了但没人读，等于没实现

README 里对着 `position` 与 `float` 说这句话：它们解析进了计算样式，但布局侧没有消费方。既然如此，那就不算支持。

这条口径往下影响的是写法：功能没做完不写进代码，不拿「先占个位置」的字段顶着。文档里也一样，字段存在不构成支持。
